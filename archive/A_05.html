Using Regular Expressions in SAP by “Brute Force”

Gianmarco Corradini, 15.06.2025

SAP is highly effective when data can be searched through predefined fields such as document number, posting date, account, vendor, customer, company code, or fiscal year.

However, SAP becomes less flexible when the user needs to search for patterns inside textual fields. For example, it may be necessary to find an invoice number containing a particular sequence of characters, a document with a specific reference structure, or a journal entry whose text follows a recurring format.

Regular expressions provide a natural solution to this problem, but they are generally not available in standard SAP search transactions. A simple workaround is therefore to export the journal entries from SAP and search them externally with Python.

I refer to this approach as using regular expressions in SAP by brute force. The regular expression is not executed inside SAP. Instead, the accounting data is extracted from SAP and processed locally with a program that supports regex.

The Basic Idea

The procedure consists of four steps:

  1. Export the journal entries from SAP into a text file.
  2. Read the exported file with Python.
  3. Apply a regular expression to the exported entries.
  4. Return or print only the accounting documents that match the pattern.

The search is therefore moved from SAP to Python. SAP remains responsible for storing and exporting the accounting data, while Python performs the pattern recognition.

This is a brute-force approach because the program can scan the complete export, document by document, until it finds all occurrences of the requested pattern.

Why Regular Expressions Are Useful

A standard SAP filter normally searches for a known value in a known field. Regular expressions are more general. They describe the structure of the value rather than only its exact content.

Suppose, for example, that an invoice number consists of five digits and always begins with the number 2. The corresponding regular expression could be written as: 

^2\d{4}$

This expression means:

  • ^ marks the beginning of the string;
  • 2 requires the first character to be 2;
  • \d{4} requires exactly four additional digits;
  • $ marks the end of the string.

The expression would match values such as: 

20001
24567
29999

It would not match values such as: 

12345
2000
200001

This distinction is difficult to express with an ordinary text filter, but it is immediate with regex.

Exporting the Journal Entries

The first step is to extract the journal entries for the relevant company code, fiscal year, posting period, or account selection.

The exact SAP transaction used for the export is not essential to the method. What matters is that the result contains the accounting documents and can be saved as a text-based file.

Depending on the SAP environment, the export may contain fields such as:

  • company code;
  • document number;
  • fiscal year;
  • posting date;
  • document date;
  • reference number;
  • document header text;
  • G/L account;
  • vendor or customer number;
  • line-item text;
  • debit and credit amounts.

Once the file has been downloaded, the information can be treated as ordinary text. At that point, the limitations of the SAP search interface no longer apply.

Reading the Export with Python

In my implementation, Python opens the exported SAP file and reads its contents. The program then uses regular expressions to identify the boundaries of the accounting documents and to search within them.

In simplified form, reading a text export can be represented as follows: 

with open("sap_export.txt", "r", encoding="utf-8") as file:
    sap_data = file.read()

The variable sap_data now contains the complete exported journal as a string.

A regular expression can then be applied through Python's re module: 

import re

pattern = r"^2\d{4}$"
matches = re.findall(pattern, sap_data, re.MULTILINE)

The actual program is more structured because the objective is not merely to return isolated strings. The useful result is normally the complete journal entry or accounting document in which the pattern appears.

Searching Complete Accounting Documents

One important feature of the method is that the search does not need to be restricted to a single SAP field.

After the export, an accounting document can be treated as a block of text. The regular expression can therefore search across the information associated with the complete document.

For example, it is possible to search for a document containing:

  • a particular invoice-number structure;
  • a specific sequence in the reference field;
  • a word in the document header;
  • a particular G/L account;
  • a vendor or customer number;
  • a recurring line-item description;
  • a combination of several patterns.

This can be particularly useful when the exact value is unknown but its structure is known.

For example, the user may remember only that an invoice reference contains the letters INV, followed by a year and a sequence number: 

INV-2026-00451

A possible regex would be:

INV-\d{4}-\d+

The program can scan the complete export and return every accounting document containing a reference with this structure.

Searching the Document Header and Line Items

The exported accounting document can also be divided into logical components.

For example:

  • the document header;
  • the individual accounting line items.

This distinction allows the search to be more precise. A pattern may be searched only in the header, only in the line items, or in the complete accounting document.

Suppose that the objective is to find every document whose header text contains the word Anwalt. A case-insensitive search could be performed with: 

pattern = r"\bAnwalt\b"

result = re.search(
    pattern,
    document_header,
    re.IGNORECASE
)

If the pattern is found, the program can print the complete document, including all related postings.

This is useful because the searched text provides the identification criterion, while the full journal entry provides the accounting context.

Searching for Character Sequences

The original motivation for my program was the need to search for invoices or accounting documents containing a specific sequence of characters.

Sometimes the complete reference is not known. Only a part of the identifier is available. In other cases, several documents follow a similar naming convention.

A basic substring search can already be useful: 

pattern = r"ABC123"

However, regex makes it possible to generalize the search: 

pattern = r"ABC\d{3}"

This expression searches for the letters ABC followed by exactly three digits.

It would therefore match:

ABC001
ABC123
ABC999

The search is no longer limited to one known invoice. It identifies an entire class of references sharing the same structure.

Combining Multiple Conditions

The external search can also combine multiple conditions.

For example, a document may be returned only when it contains both a particular reference structure and a specific G/L account: 

reference_found = re.search(
    r"INV-\d{4}-\d+",
    document
)

account_found = re.search(
    r"\b440000\b",
    document
)

if reference_found and account_found:
    print(document)

This creates a simple form of document-level filtering.

The conditions can be extended to represent more specific accounting investigations. For example, the program may search for documents that contain:

  • one expense account;
  • one vendor number;
  • a particular textual description;
  • an invoice reference matching a defined structure.

These conditions would normally require several SAP filters or repeated manual searches. In Python, they can be evaluated within the same document block.

Why I Call It “Brute Force”

The expression brute force is used here informally.

The method does not integrate regular expressions into SAP. It bypasses the limitation by exporting the data and scanning the resulting file.

Conceptually, the program performs the following operation:

\[ \text{Matching documents} = \left\{ d \in D : R(d) = 1 \right\}, \]

where:

  • \(D\) is the set of exported accounting documents;
  • \(d\) is one accounting document;
  • \(R\) is the regular-expression search rule;
  • \(R(d)=1\) means that the document satisfies the pattern.

Every exported document is evaluated. If the regular expression matches, the document is retained. Otherwise, it is discarded.

The method is direct and computationally simple. It does not require a sophisticated SAP extension, a custom report, or ABAP development.

Practical Advantages

This approach offers several practical advantages.

Full Regex Support

Python supports advanced regular-expression features such as character classes, repetitions, alternatives, groups, optional elements, and lookarounds.

No SAP Customization

The method does not require changes to the SAP system. It can be used by an accounting user who is able to export the journal entries and run a local Python script.

Reusable Searches

Once a pattern has been defined, it can be stored and applied again to future exports.

Document-Level Analysis

The search can consider the entire accounting document rather than only one field at a time.

Flexible Output

The program can print matching documents, save them into another text file, export them to CSV, or transform them into a structured table for further analysis.

Limitations

The method also has some limitations.

First, it does not search live SAP data. It searches only the data included in the export.

Second, the reliability of the program depends on the structure of the exported file. If the SAP layout changes, the parsing logic may need to be adjusted.

Third, the export must contain enough information to identify and reconstruct the relevant accounting documents.

Finally, exported accounting data may contain confidential information. The file should therefore be handled in accordance with the company's data-security and retention policies.

Potential Applications

The same method can support several accounting and control activities, including:

  • searching for incomplete invoice references;
  • identifying recurring naming structures;
  • finding documents containing unusual character sequences;
  • locating postings associated with a particular external system;
  • detecting inconsistent reference formats;
  • searching document texts during reconciliations;
  • supporting internal accounting investigations;
  • performing simple data-quality controls.

The method is especially useful for one-off investigations where creating a dedicated SAP report would be disproportionate.

Conclusion

Standard SAP transactions provide powerful structured filters, but they do not normally provide the flexibility of regular expressions.

A practical workaround is to export the journal entries and search them externally with Python. The program reads the exported file, separates or identifies the accounting documents, applies a regex pattern, and returns the relevant entries.

This does not introduce regex into SAP in a technical sense. Instead, it extends the analysis process outside SAP.

For this reason, the method can be described as using regular expressions in SAP by brute force: the data is extracted, every relevant accounting document is scanned, and the limitations of the SAP search interface are overcome through external processing.
